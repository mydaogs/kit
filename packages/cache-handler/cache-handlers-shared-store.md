# Distributed cache handler for multi-deployment apps

## Context

An app that ships as several deployments (one per locale, region, or tenant) shares nothing in memory. `revalidateTag` and `updateTag` from `next/cache` invalidate only the calling deployment's in-process cache, so a mutation on one deployment leaves peers stale. HTTP fan-out to peers is rejected because invalidation cost must stay `O(1)` regardless of deployment count

## Decision

Use Next.js's built-in `cacheHandlers.default` to route all tag-invalidation timestamps through a shared Redis instance. Cache values remain in each deployment's in-process memory (deployment-specific rendered output must not leak across deployments). Tag invalidation timestamps are global: a single Redis pipeline write per `revalidateTag` / `updateTag` is visible to every deployment on its next throttled `refreshTags()` poll

Two shared packages provide the mechanism:

- `@shared/kv` — shared Redis client. The `./rest` entrypoint has no `server-only` import so it can safely load inside Next runtime infrastructure (the cache-handler file). The default entrypoint re-exports the same singleton with `server-only` for normal app code. Both entrypoints expose native `.mjs` runtime files because Next loads cache handlers outside the normal app transpilation path. The client is built lazily behind a `Proxy` so `process.env` is read at first request rather than at module load, which on a serverless host happens during build-time tracing with no runtime env vars
- `@shared/cache-handler` — exports `createDistributedCacheHandler({ appName, kvClient })` returning the Next `CacheHandler` object. It stores cached streams as buffered bytes, reconstructs a fresh `ReadableStream` on every hit, and keeps a bounded in-process LRU (default 5,000 entries / 50 MB). Redis stores only tag invalidation timestamps, never rendered values. `src/*.ts` is the source of truth; `runtime/*.mjs` is generated by a `sync-runtime` script and verified by the package `check-types` script

A thin ESM shim (`cache-handlers/distributed.mjs`) wires the factory into each app with the correct `appName`. Redis keys are scoped by `NEXT_CACHE_NAMESPACE` and app name so dev/preview/prod can share one instance safely and apps do not accidentally invalidate each other. `NEXT_CACHE_NAMESPACE` is required whenever the Redis env vars are present

If Redis env vars are absent, the factory falls back to an in-memory-only handler so local single-process dev still works

## Mechanism details worth preserving

- A ZSET acts as the delta index for `refreshTags`; a per-tag key carries the `(stale, expired)` tuple. Both are needed: without the tuple, an SWR-style bump from a peer collapses into hard invalidation on the receiving side
- An entry is expired only when the expire timestamp is in the past **and** the entry was created before it. Without the `<= now` guard, a future-dated expiry immediately invalidates the entry instead of serving it stale-while-revalidate until the deadline
- `refreshTags` is throttled with jitter and deduplicates concurrent calls behind a single in-flight promise
- Tag-state maps rely on `Map` insertion order for LRU eviction: re-inserting a bumped tag moves it to the tail so the cap drops least-recently-bumped tags first
- Dropping a tag from the local stale/expired maps would let any cached entry that depended on it read as fresh again — soft tags are passed at read time and are not recorded on the stored entry, so the dependents cannot be identified. Conservative correctness: clear all stored entries whenever any tag state is dropped, mirroring a process restart. The overflow paths that trigger this fire rarely, so the cold-cache cost is bounded
- Old bump entries are trimmed opportunistically (low probability per call) rather than on a schedule

## Production output tracing

Next's production output tracing does not discover the cache-handler path from normal route imports, so each app must explicitly include `./cache-handlers/**/*`, the cache-handler and kv runtime files, and the Redis runtime dependency through `outputFileTracingIncludes`. The app-local shims import the generated runtime files by relative path and pass a lazy file URL for the KV runtime so production functions do not rely on workspace package symlinks for this critical loader path

`outputFileTracingRoot` should only be set outside a managed host: hosts that derive deployment paths from a configured app root can look for build manifests one directory too high when the trace root is overridden

The distributed handler and its tracing includes are disabled during normal local `next dev`. Local development uses Next's built-in in-memory handler unless an explicit opt-in env var is set. This keeps the dev bundler from indexing production-only trace globs and avoids retaining large rendered cache entries while editing

## Deployment env checklist

Every deployment that enables shared Redis invalidation must define:

- `UPSTASH_REDIS_REST_URL` — shared Redis REST URL
- `UPSTASH_REDIS_REST_TOKEN` — shared Redis REST token
- `NEXT_CACHE_NAMESPACE` — mandatory cache namespace; use the same value for deployments that should share invalidation and a distinct value per environment
- `NEXT_DISTRIBUTED_CACHE_IN_DEV` — optional local-only opt-in for testing the distributed handler under `next dev`

Preview or development deployments must use a different namespace from production

## Client-side identity transition invalidation

An app that persists the TanStack Query cache to `localStorage` has a matching problem on the client: cache keys are unscoped static strings, so a previous user's private data would be restored and served to the next user on the same browser

Rather than scoping every key or maintaining a denylist, a **central watcher** (`useResetCacheOnIdentityChange`) handles this. It:

- Captures the first available session as a baseline (this is the restored-from-localStorage identity on a reload)
- Detects when the session identity (`user.id` + `activeOrganizationId` + `activeMemberId`) changes
- On any transition, removes private query keys and drops the persisted snapshot immediately
- Leaves the session query invalidated but not removed, so role-gated queries stay mounted while the refreshed session resolves
- Leaves public/reference keys untouched so public data stays cached across transitions

Unknown application keys must **fail closed** — removed rather than retained — so a forgotten key cannot leak across an identity boundary

Because the session query itself can be restored from the persisted cache, the persistence provider starts one authoritative fresh session fetch from its restore callback. The fetch is intentionally fire-and-forget: awaiting it would delay every restored query, including public data. It begins before restoration completes, so restore-sensitive routes use `useIsRestoring()` together with session success/fetch state instead of relying on mount-local `isFetchedAfterMount`

## CDN policy audit

Expose a named-policy union rather than a free-form `{ revalidate, expire }` API, so freshness windows are explicit and auditable:

- `livePublic` — `s-maxage=15`, `stale-while-revalidate=120` (fast-moving record state)
- `homepagePublic` — `s-maxage=30`, `stale-while-revalidate=300` (homepage feed surfaces)
- `directoryPublic` — `s-maxage=60`, `stale-while-revalidate=600` (public lists and profiles)
- `aggregatePublic` — `s-maxage=60`, `stale-while-revalidate=3600` (cron-driven aggregate endpoints)

## Cross-app invalidation

A writer app that needs to invalidate a reader app's deployments does not register its own distributed cache handler. It uses an explicit publisher API instead:

- `publishCacheInvalidation({ kvClient, targetAppName, tags, mode })` writes directly to the same Redis keys the handler reads from (`next-cache:{NEXT_CACHE_NAMESPACE}:{targetAppName}:tag:{tag}` and `:tag-bumps`)
- The writer app passes its own `kv` singleton from `@shared/kv/rest` as `kvClient`. cache-handler intentionally has no runtime dependency on `@shared/kv` so the precompiled `runtime/*.mjs` files contain no bare workspace specifiers — reader apps load those files outside Next's transpile pipeline, and an unresolvable bare specifier there fails on a serverless host's flattened layout. `KvClient` / `KvPipeline` are exported as structural interfaces so any Redis-compatible client is assignable
- This avoids the misconfiguration where wiring a writer app with the reader app's `appName` would mix LRU keys across deployments
- The writer app does **not** need to register a reader distributed cache handler for cross-app invalidation. If its own admin views later adopt `"use cache"`, a handler may be added with the writer app's own `appName` (its own keyspace), independent of the publisher

Invalidating the function-level cache does not purge a CDN. An edge cache continues serving until its own `s-maxage` window elapses and it re-checks with the function — at which point the function sees the bump and rebuilds

## Publisher error semantics

`publishCacheInvalidation` propagates Redis pipeline errors to callers rather than swallowing them. A Redis outage during an admin save surfaces as a save error in the admin UI; a Redis blip during a seed halts the seed. If seed robustness against transient failures is needed, wrap the seed-step-level writes in a try/catch rather than weakening the publisher. The publisher is intentionally strict because silent invalidation failures lead to hard-to-debug state drift across deployments

The handler's own `updateTags` is the opposite: it wraps its Redis pipeline in try/catch and logs, so the peer-instance write behind an ordinary `revalidateTag` can fail invisibly. Same-app peer delivery is therefore **not** observable through `revalidateTag` alone. A caller that gates durable state on delivery having happened must publish its own `appName`'s namespace through `publishCacheInvalidation` and await it. Publishing a namespace the handler also writes is idempotent: it is the same key pair

## Consequences

- Cross-deployment invalidation latency is bounded by `refreshThrottleMs` (default ~1000 ms with jitter)
- Cache values are discarded on deploy
- Cross-app invalidation is tag-only; path invalidation is not used across apps because route trees differ
